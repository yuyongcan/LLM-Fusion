# MOPD 外推与投影（2026-09-20）

## 研究问题

**H1 —— 外推。** 蒸馏落到一个比合并更短的 task vector（‖τ_MOPD‖ = 1.6356 对 ‖τ_merge‖ = 2.3058），分数却大致相当（65.45 对 66.00 AVG8）。那么沿该方向再往前走是否还有未兑现的增益，即 θ_base + α·τ_MOPD 在 α > 1 时是否会变好？

先验判断：不会。合并自身的系数扫描在 c = 1.0 之后就不再有回报了（从 c=1.0 到 c=1.2，pass@16 80.28 → 80.11，mean@16 66.00 → 65.08），而 τ_MOPD 是一个单一的混合方向，无法像 τ_merge 那样逐域重新缩放。

**H2 —— 冗余。** τ_merge 的大部分是否在功能上是惰性的？把它相对 τ_MOPD 分解：

    c        = <τ_merge, τ_MOPD> / ‖τ_MOPD‖²  = 0.6449
    parallel = c · τ_MOPD                       ‖·‖ = 1.0560
    perp     = τ_merge − c · τ_MOPD             ‖·‖ = 2.0497

如果平行部分保留了合并的大部分推理能力，那就说明蒸馏找到了一条通往同一功能的更短路径，而 τ_merge 的其余部分是冗余的 —— 这也能解释为什么 MOPD_merge1.0 在 lcb_v5（67.44 对 67.10）和 gpqa（64.49 对 63.60）上超过了三专家合并。

平行分量必然更短，所以每一项对比都需要 `*_normmatched` 变体，即把每个分量重新缩放回 ‖τ_merge‖。没有这个对照，就无法把分数下降归因于方向而非更新幅度。与 `../20260916_norm_matched_subsets` 同样的纪律。

## 精度：复用这些脚本之前请先读这一节

task vector 相对权重本身很小（‖τ‖/‖θ_base‖ ≈ 0.1%），因此其中很大一部分元素低于一个 bfloat16 舍入单位。在几何门禁发现问题之前，有三个地方分别破坏过 task vector 的运算：

1. **`verl/model_merger` 以 bf16 导出。** 它在重组分片时把 fp32 的 FSDP master weights 用 `.bfloat16()` 做了转换。改为 fp32 重新导出后，‖τ_MOPD‖ 从 1.4259 变为 1.6356，且两者方向相差 cos = 0.679。在一个代表性的张量中，τ 的 70.7% 元素在 bf16 导出里**恰好为零**，而在 fp32 中一个都没有。已修复：增加 `--save_dtype`，默认 float32。

2. **`from_config` 会静默地重新舍入。** `AutoModelForCausalLM.from_config` 会遵循 `config.torch_dtype`，而基座模型该值是 bfloat16，于是 `load_state_dict` 把 fp32 state 舍入进了 bf16 参数，之后的 `.to(float32)` 只是把**已经舍入过**的值加宽 —— 产出一个 15 GB 的「fp32」checkpoint，里面装的却是 bf16 数据。用 `(t.to(torch.bfloat16).to(t.dtype) == t).all()` 可以检测。此处的两个脚本现在都在构造模型前钉住 `config.torch_dtype`。

3. **双重舍入。** 从一个已经是 bf16 的导出构建 θ_base + α·τ，再以 bf16 存储，会把 α = 1.15 塌缩成实际生效的 1.02。应当从 fp32 端点构建并以 fp32 存储。

**推理精度是另一个问题。** 无论 checkpoint 怎么存，vLLM 都会转成 bf16，而且该转换是对同样的值做同样的操作，所以重新评测一个 fp32 导出会精确复现 bf16 的分数。**fp32 存储对下游运算和分析有意义，对评测保真度没有意义。**

推理精度真正改变的是*有效*系数 —— 即转换后存活下来的 ‖τ‖ 份额，在全模型上测量：

| 名义 c | merge5 生效值 | MOPD 生效值 |
|---|---|---|
| 0.4 | 0.2858 (71.5%) | 0.2417 (60.4%) |
| 0.6 | 0.4979 (83.0%) | 0.4347 (72.5%) |
| 0.8 | 0.7305 (91.3%) | 0.6457 (80.7%) |
| 1.0 | 0.9663 (96.6%) | 0.8718 (87.2%) |
| 1.2 | 1.1966 (99.7%) | 1.1075 (92.3%) |

两个后果：已发表系数扫描的**低端是被打了折的**（c=0.4 丢掉了它应有更新的 28.5%）；而且小的 task vector 比大的损失更多，所以 bf16 推理对蒸馏的惩罚大于对合并的惩罚。`run_precision_control.sh` 对两者都做了检验。

把 τ 放大确实能恢复保真度，但恢复得极慢，慢到不足以当作修复手段 —— cos(rounded, τ) 在 α=1.15 时只从 0.679 走到 0.715，要到 α=3 才达到 0.909，而那时归一化误差仍有 43.8%。放大是一阶的，保真度恢复是二阶的，两者无法分离。fp32 推理才是干净的对照。

## 几何（所有端点均为 fp32）

```
||theta_base|| = 1583.4033        (398 shared float tensors)

model      ||tau||     cos to MOPD    cos to merge5
MOPD        1.6356        1.0000         0.4580
merge5      2.3058        0.4580         1.0000
a1.15       1.8809        1.0000         0.4580
a1.30       2.1262        1.0000         0.4580
par         1.0560        1.0000         0.4580
par_nm      2.3058        1.0000         0.4580
perp        2.0497        0.0000         0.8890
perp_nm     2.3058        0.0000         0.8890
```

每一项构造断言都精确成立：‖τ_a1.15‖ = 1.15 × 1.6356，平行分量与 τ_MOPD 共线，垂直分量与它正交，两个 norm-matched 变体都位于 ‖τ_merge‖。

注意在两个端点都是 fp32 时 cos(MOPD, merge5) = **0.4580**，而只有 MOPD 是 fp32 时是 0.3555，两者都是 bf16 时是 0.3231。请报告 fp32 那个数；其余的都低估了对齐程度。作为尺度参照：该维度下两个随机向量的 cos ≈ 1.6e-5，而五个专家两两正交到 [−0.0006, 0.0222] 之内 —— 所以 0.458 是**强**对齐，不是近乎正交。

## 运行方式

```bash
# H1 + H2 筛选：8 个模型，三列基准，n=4，bf16 推理（即所报告的配置）
bash research/experiments/20260920_mopd_extrapolation/run_h1h2_sweep.sh

# 精度对照：3 个模型 × {bfloat16, float32}，同样的列
NGPUS_PER_NODE=16 bash research/experiments/20260920_mopd_extrapolation/run_precision_control.sh
```

两者都需要先起好代码 sandbox（`bash setup_sandbox.sh`），否则 lcb_v5 会**静默腰斩**；两者都会跳过已完成的工作。

三列基准分别是：aime25（对锐化最敏感 —— 在 c=1.0 到 c=1.2 之间，合并在该列丢了 5.4 个 mean@16 点）、ifbench（合并真正拓宽了 pass@16 的唯一一条轴，+19.0）、lcb_v5（最大的代码集，因此噪声最小）。

## 事先固定的判定规则

- **H1**：α=1.15 必须在三列上的平均表现超过 α=1.0 达 +1.0 以上，才值得跑完整的 n=16。与已部署的 bf16 MOPD 对比；在 bf16 推理下 α=1.15 提供的是基线有效更新的 1.20×。
- **H2**：若 `proj_parallel_normmatched` 在 lcb_v5 上保持在 merge5 的 2 个点以内，则冗余解读成立，并值得跑完整的 n=16。若 `proj_perp*` 表现更好，则 H2 被证伪 —— 两种情况都要记录。
